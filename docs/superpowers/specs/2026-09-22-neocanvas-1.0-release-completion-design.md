# NeoCanvas 1.0 Release Completion Design

## Objective

Finish the existing NeoCanvas application as a commercial iPad 1.0 release candidate without redesigning it, expanding scope, removing working functionality, or breaking compatible `.neocanvas` documents.

NeoCanvas is already feature-complete. This phase addresses only evidence-backed release blockers: crashes, data-loss risks, incorrect save/load or recovery behavior, broken undo/redo, import/export faults, iPad build/runtime problems, Pencil or touch regressions, accessibility defects that prevent use, and App Store handoff failures.

## Source and concurrency contract

All work remains on `ipad-gestures-phase1` in `neoworkssuite/Canvas-Mac`. Before every source or documentation change:

1. Fetch `origin` and compare local `HEAD` with `origin/ipad-gestures-phase1`.
2. Inspect any intervening commits before continuing.
3. Preserve concurrent changes and fast-forward or rebuild local changes onto the live tree.
4. Push normally; never force-push.

The known starting candidate is `b9945e81bac009a4d123f2eb00d45604f22b1dba`, but the live remote branch is authoritative.

## Release-validation flow

Release work follows one directional gate:

1. Confirm the exact candidate tree has a successful ordinary fast-validation run.
2. Investigate only concrete failures or uncovered release risks.
3. For a code defect, add the narrowest regression test that reproduces it, implement the smallest compatible fix, and rerun affected tests plus the release-contract verifier.
4. Push an ordinary commit and wait for its fast-validation result.
5. When no fixes remain and fast validation is green, create one same-tree, no-code commit whose message contains `[ipad]`.
6. Query the full Apple lane and treat the candidate as validated only after that exact commit completes successfully.

Do not stack speculative `[ipad]` jobs. The older checkpoint `a02c6f577f2a43f5f86c1fdf02704fddc7babf0e` may validate the Swift `URLSession` update bridge and related release UX, but it does not validate newer candidate commits.

## Automated evidence

The automated gate must verify:

- shared Kotlin tests;
- the release contract for version `1.0.0`, build `1`, bundle ID `com.neoworksuite.neocanvas`, iPad-only distribution, icons, privacy manifest, encryption declaration, and orientations;
- iPad Simulator compilation, installation, launch liveness, light/dark screenshots, and three cold relaunches;
- ARM64 Kotlin framework compilation;
- unsigned Release-iphoneos application compilation and packaged-resource checks.

Existing workflow behavior is preserved unless a concrete failure shows the workflow itself is defective.

## Manual physical-iPad evidence

CI cannot complete physical interaction acceptance. The release checklist must continue to distinguish automated evidence from checks requiring a person using an iPad and Apple Pencil.

Physical acceptance covers:

- Gallery card tap, explicit Open, Files picker open/cancel/error, rename, duplicate, Stack, and trash deletion;
- immediate Redo reactivity and sequential history across raster, layer, Liquify, Arrange, and effect operations;
- Portrait/Landscape New Canvas cards, presets, custom dimensions, the 16 MP safety limit, and the locked Background plus active Layer 1;
- Kids Mode visibility and persistence;
- non-exporting workspace backdrop grid;
- Premium Pill controls with Pencil and finger;
- automatic and manual update checks, mocked newer-version prompt, Later, App Store handoff, and non-blocking network failure;
- PNG, JPEG, PDF, TIFF, PSD, and native `.neocanvas` save/load behavior, including dimensions, background/transparency, colour, editable objects, clipping, masks, and PSD compatibility behavior;
- Apple Pencil pressure, fast strokes, large brushes, gestures, portrait, and landscape.

Items are checked in `docs/release-checklist.md` only when the corresponding evidence exists. Simulator evidence never substitutes for physical-device evidence.

## Compatibility and safety constraints

- Preserve existing `.neocanvas` compatibility wherever reasonably possible.
- Preserve the real locked white Background layer and active raster Layer 1 for new documents.
- Preserve recovery snapshots after failed saves and retire them only after successful save or explicit Start Fresh.
- Preserve atomic iPad file writes and Gallery delete-to-trash behavior.
- Preserve the Swift-owned `URLSession` update lookup through `NativeUpdateLookup`; do not restore historical direct Kotlin/Foundation implementations.
- Preserve App Store-mediated updates; NeoCanvas must not download or install executable updates.
- Keep 1.0 distribution iPad-only.
- Do not add unrelated features or presets.

## Error handling

Failures must remain visible and recoverable. A failed save keeps the editor and recovery state intact. Invalid external documents produce a useful error without adopting a Gallery save target. Update-network failures do not block app use. Export failures do not destroy the source document. CI failures are diagnosed from the failing job and logs rather than bypassed or relabeled as success.

## Completion criteria

NeoCanvas 1.0 is software-complete when:

- ordinary fast validation succeeds for the exact candidate;
- full `[ipad]` validation succeeds for that same tree;
- no reproducible core crash or known data-loss defect remains;
- Gallery opening, history, save/load/recovery, New Canvas, Kids Mode, updates, and primary exports pass the applicable automated and physical checks;
- Apple Pencil and orientation acceptance pass on a physical iPad;
- release identity and App Store material are ready.

After this gate, feature development stops. The next phase is signed Archive, TestFlight, final physical beta acceptance, and App Store submission.
